# Постоянные MCP-демоны cod-doc

Один процесс на профиль обслуживает все харнессы сразу по `streamable-http`,
вместо того чтобы каждый клиент порождал собственный stdio-субпроцесс.

| Демон | Порт | Профиль | Тулов |
|---|---|---|---|
| `com.cod-doc.mcp` | 8801 | `standard` | 112 |
| `com.cod-doc.mcp-agent` | 8802 | `agent` | 6 |

Профиль применяется деструктивно (`apply_profile` удаляет записи из каталога
`mcp._tool_manager._tools`), поэтому один процесс = ровно один профиль. Клиент
выбирает профиль портом, а не флагом.

## Установка

```bash
./cod-doc-mcp-daemon.sh install     # отрендерить plist'ы и загрузить
./cod-doc-mcp-daemon.sh status      # что загружено и отвечает ли порт
./cod-doc-mcp-daemon.sh restart     # перечитать бинарь после апгрейда
./cod-doc-mcp-daemon.sh uninstall   # выгрузить и удалить plist'ы
```

Бинарь берётся из `COD_DOC_MCP_BIN`, иначе из `~/.cod-doc/runtime/bin/cod-doc-mcp`.

**Демон обязан смотреть на пиннованную non-editable сборку.** Editable-инстал
рабочего дерева означает, что любая правка, ребейз или незавершённый мёрдж
мгновенно уезжают во все харнессы машины одновременно. Апгрейд — осознанное
действие: пересобрать колесо, затем `restart`.

## Регистрация в клиенте

```json
{ "type": "http", "url": "http://127.0.0.1:8801/mcp" }
```

Всё. `--profile` в клиентский конфиг больше не пишется.

## Резолв проекта на общем сервере

`project` **обязателен** в каждом DB-туле. Под stdio процесс был равен сессии,
и `set_default_project` хранил дефолт в памяти процесса. У общего демона этого
равенства нет: `stateless_http` создаёт транспорт на запрос, но состояние
модуля общее, и процесс-глобальный дефолт означал бы, что один клиент молча
переадресует вызовы всех остальных в свой проект.

Поэтому под HTTP дефолта нет вовсе — `set_default_project` отказывает, а вызов
без `project` возвращает внятную ошибку вместо тихой работы не с той БД.
`capabilities()` показывает это в `session.shared_server`. Под stdio поведение
не изменилось. Детали — `cod_doc/mcp/tools/_workspace.py`.

Отсюда следствие: проект обязан быть в реестре `~/.cod-doc/config.yaml`.
Discovery по дереву вверх от cwd (`_discover_workspace_projects`) у демона не
работает — рабочий каталог заморожен.

## Схема БД

Перед первым запуском догнать схему во всех проектах:

```bash
cod-doc project migrate --all
```

Для hub-записей (у которых в реестре задан `db_url`) расхождение
`alembic_version` с головой кода валит сессию на открытии
(`SchemaMismatchError`). У embedded-записей такой проверки нет — устаревшая БД
откроется молча и сломается позже на уровне ORM. Поэтому прогон обязателен,
а не гигиеничен.

Не гонять `alembic upgrade` из воркtree по общей БД: миграция, которой нет в
main, делает базу нечитаемой для основного чекаута.

## Безопасность

Аутентификации у MCP-эндпоинта нет: `FastMCP` создаётся без
`auth_server_provider` и без `token_verifier`. Единственный контроль — bind на
`127.0.0.1`. Не выставлять порты наружу и не ставить `FASTMCP_HOST=0.0.0.0`.

Токен в заголовке клиента был бы театром — сервер его не проверяет.
