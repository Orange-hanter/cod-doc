# Постоянные сервисы cod-doc (macOS launchd)

Три процесса под launchd, и все три смотрят на **одну** пиннованную
non-editable сборку в `~/.cod-doc/runtime`:

| Сервис | Порт | Что это |
|---|---|---|
| `com.cod-doc.mcp` | 8801 | MCP, профиль `standard` |
| `com.cod-doc.mcp-agent` | 8802 | MCP, профиль `agent` |
| `com.cod-doc.web` | из `api_port` конфига | REST API + web UI (`cod-doc serve`) |

Профиль применяется деструктивно (`apply_profile` удаляет записи из каталога
`mcp._tool_manager._tools`), поэтому один процесс = ровно один профиль. Клиент
выбирает профиль портом, а не флагом.

`:8802` — не task-centric surface. С RFC 25 §3.2/§3.5 (CUR-007/008/016) 6 тулов
профиля `agent` — куратор документации: `agent_capabilities`, `curator_next`,
`ctx_search`, `ctx_drift`, `context_get`, `agent_report`. `agent_capabilities()`
отдаёт `role: "doc-curator"` и `forbidden: [agent_pick, task_checkout,
task_complete]`. Точка входа в работу — `curator_next(project=...)`: doc card с
очередью «что протухло и за что браться первым». Coding-агенту, которому нужен
`agent_pick`/`task_checkout`, идти на `:8801` (`standard`, 143 тула), а не на
`:8802`.

## Команды

Управление живёт в самом `cod-doc` (ADO-192): `deploy/` не входит в колесо,
поэтому из установленного рантайма bash-скрипт был недоступен вовсе.

```bash
cod-doc update                       # рантайм → схема → сервисы → починка
cod-doc update --dry-run             # показать план и выйти, ничего не трогая
cod-doc update --ref <sha>           # конкретная ревизия вместо ветки remote'а
cod-doc update --install-services    # после свапа не kickstart, а install plist'ов

cod-doc runtime status               # загружено / отвечает ли порт / какая версия
cod-doc runtime version              # версии всех установок на машине
cod-doc runtime build [--ref <sha>]  # собрать и проверить, ничего не подменяя
cod-doc runtime rollback             # вернуть предыдущий рантайм
cod-doc runtime restart              # перечитать бинарь без пересборки
cod-doc runtime install              # отрендерить plist'ы и загрузить
cod-doc runtime uninstall            # выгрузить и удалить plist'ы
cod-doc runtime render               # показать plist'ы, ничего не записывая
```

`update` (алиас `upgrade`) — четыре фазы одной командой и одним подтверждением:

| Фаза | Что делает | Обратимо |
|---|---|---|
| A · рантайм | сборка ревизии в `.staged`, свап, установка в PATH | свап — да (`cod-doc runtime rollback`), PATH — нет |
| B · миграции | схема всех проектов реестра догоняется **новым** бинарём | нет |
| C · сервисы | `launchctl kickstart -k` (или `install` при `--install-services`) | да |
| D · починка | `doc import` дрейфа, реестр хэшей, ссылки, протухшие замки | нет |

Фазы снимаются флагами `--skip-install` / `--skip-migrate` / `--skip-repair`;
`--skip-links` оставляет фазу D, но без link backfill — он обходит каждую
секцию корпуса и на больших проектах и есть основная стоимость прогона.
`-p <slug>` (повторяемый) ограничивает фазы B и D одним проектом; фаза A
машинная и скоупа не имеет.

`--ref` без аргумента берёт ветку remote'а. Явная ревизия обязана быть её
предком — иначе команда откажет. Это не формальность: катить локальную ветку
значит поставить в живые сервисы код, который не проходил CI. Откат на прошлый
релиз делается тем же `update --ref <старый-sha>`.

Откат рантайма (`cod-doc runtime rollback`) возвращает прежний код, но **не**
откатывает БД: накатанные фазой B миграции остаются, и прежний код может не
знать новой схемы.

### Коды выхода и неинтерактив

| Код | Что значит |
|---|---|
| 0 | всё удалось |
| 1 | какая-то из фаз провалилась — машина в промежуточном состоянии |
| 2 | так звать нельзя: неизвестный флаг, либо не-TTY без `--yes` |
| 3 | сборка отвергнута и свап откачен — машина осталась на прежней версии |

3 отделён от 1 намеренно: для автоматики «ничего не изменилось, плохая сборка»
и «половина сделана» — разные ситуации. 78 не переиспользуется, его занял
launchd под `bad interpreter`.

Не-TTY плюс необратимое действие без `--yes` — это выход 2 с подсказкой про
`--yes` и `--dry-run`, а не тихое продолжение и не зависший `click.confirm`.
Под launchd и в скриптах это и есть рабочий режим: `cod-doc update --yes --json`
печатает в stdout ровно один объект, весь прогресс и таблицы — в stderr.

### Первая установка

На машине, где cod-doc нет вовсе, `cod-doc runtime install` звать нечем: он
требует уже собранного рантайма. Для этого случая — и только для него —
остался `deploy/launchd/cod-doc-services.sh`: он ставит cod-doc в PATH из
чекаута (`uv tool install --from <repo>`) и сразу отдаёт ему управление
(`cod-doc update --install-services`). Старые подкоманды скрипта отвечают, куда
переехали, и ничего не делают.

## Почему именно так

**Сервисы не смотрят в рабочее дерево.** Editable-инстал означает, что любая
правка, ребейз или незавершённый мёрдж мгновенно уезжают во все харнессы
машины одновременно, а `KeepAlive=true` выкатывает их автоматически при первом
же падении. Веб-UI жил так до ADO-189 под лейблом `com.dakh.cod-doc`;
`install` снимает его и сохраняет plist как `.plist.replaced`.

**Апгрейд собирает свежий venv, а не ставит поверх.** Установка поверх не
удаляет файлы, исчезнувшие из пакета: в рантайме накопилось 12 модулей,
которых нет в репозитории (`services/story_service.py` рядом с пакетом
`services/story_service/`, `cli/doc.py`, `infra/models.py`, …). Сегодня это
безвредно — пакет выигрывает у одноимённого модуля, — но это мёртвый код,
который никто не удалял. Сборка с нуля решает это по построению.

**Исходник — временный `git worktree` на нужном коммите, а не рабочее
дерево.** В нём лежит ровно содержимое коммита: незакоммиченное физически
не может уехать в релиз. Именно worktree, а не `git archive`, потому что в
нём есть `.git` — и setuptools-scm выводит версию сам. Экспорт архивом
требовал бы подставлять версию руками, а вывод `git describe`
(`v1.1.0-456-g53d5fec`) — не версия PEP 440.

**Свап атомарный, откат бесплатный.** Новый venv собирается в
`~/.cod-doc/runtime.staged`, проверяется импортом пакета и запуском
console-script'а и только потом встаёт на место; прежний остаётся как `~/.cod-doc/runtime.previous`.

**`uv venv --relocatable` обязателен, и smoke-тест повторяется после свапа.**
Без `--relocatable` путь `.staged` запекается в shebang каждого
console-script'а; после переезда каталога они указывают на несуществующий
путь, и launchd роняет демоны с `bad interpreter` (код 78). Проверка до свапа
этого не видит — она гоняется по пути сборки, — поэтому есть вторая, по
конечному пути, и она же откатывает свап без участия человека: живые сервисы
важнее новой версии.

**`bootout` асинхронен.** Он возвращает управление раньше, чем домен забывает
лейбл, и немедленный `bootstrap` падает с `Bootstrap failed: 5: Input/output
error`. Поэтому выгрузка ждёт, пока `launchctl print` перестанет находить
лейбл, и только затем грузит plist.

**Миграции гонит новый процесс, а не тот, что делал свап.** `alembic upgrade
head` старого кода накатит старую голову — значит фаза B обязана исполняться
уже новым бинарём. Но процесс, переживший подмену собственного venv, —
химера: `mv` это rename, уже импортированные модули целы, а `sys.path` хранит
абсолютный путь к `site-packages` рантайма, и любой следующий ленивый импорт
(а в CLI они обязательны, ADO-179) придёт уже из нового дерева. Отсюда
subprocess-relay: родитель делает свап и запускает
`<runtime>/bin/cod-doc update --resume-json -`, ребёнок исполняет фазы B–D и
владеет кодом выхода. `os.execv` отвергнут — exec в сломанную сборку убивает
того, кто мог бы откатиться. Механика целиком — в докстринге
`cod_doc/services/update_service.py`.

**Порядок фаз не такой, как был у bash-скрипта.** Скрипт поднимал демонов
сразу после свапа, а миграции оставлял человеку — и открывал окно «новый код,
старая схема»: `SchemaMismatchError` в лоб, веб отвечает 503. Теперь рестарт
(фаза C) идёт после миграций (фаза B), и демоны поднимаются уже на догнанной
схеме.

## Версии

Версия выводится из git (setuptools-scm) и печатается `cod-doc --version`:

```
$ cod-doc --version
cod-doc, version 1.1.0.post1.dev12+g4f2d4d0b1
```

До ADO-189 версия была литералом `1.1.0` в пяти местах, поэтому все установки
на машине назывались одинаково независимо от того, из какого коммита собраны.
`cod-doc runtime version` печатает все три сразу — рантайм сервисов,
`cod-doc` в PATH (uv tool) и репозиторный editable-venv.

Версия спрашивается `python -P -c 'import cod_doc'`, а не `cod-doc --version`:
`-P` не пускает cwd в `sys.path`, иначе ответ приходит из локального рабочего
дерева вместо установленного пакета — то есть проверка врёт ровно там, где
нужна. К тому же `--version` появился только в ADO-189, и опираться на него
значит уметь опознавать лишь ревизии новее самого себя.

Сборка без git (Docker: `.git/` в `.dockerignore`; распакованный sdist) даёт
`0.0.0` — признак «ревизию этой установки не опознать». CD передаёт версию
образу аргументом `COD_DOC_VERSION`.

## Регистрация в клиенте

```json
{ "type": "http", "url": "http://127.0.0.1:8801/mcp" }
```

Всё. `--profile` в клиентский конфиг больше не пишется.

## Резолв проекта на общем сервере

`project` **обязателен** в каждом DB-туле. Под stdio процесс был равен сессии,
и `set_default_project` хранил дефолт в памяти процесса. У общего демона этого
равенства нет: `stateless_http` создаёт транспорт на запрос, но состояние
модуля общее, и процесс-глобальный дефолт означал бы, что один клиент молча
переадресует вызовы всех остальных в свой проект.

Поэтому под HTTP дефолта нет вовсе — `set_default_project` отказывает, а вызов
без `project` возвращает внятную ошибку вместо тихой работы не с той БД.
`capabilities()` показывает это в `session.shared_server`. Под stdio поведение
не изменилось. Детали — `cod_doc/mcp/tools/_workspace.py`.

Отсюда следствие: проект обязан быть в реестре `~/.cod-doc/config.yaml`.
Discovery по дереву вверх от cwd (`_discover_workspace_projects`) у демона не
работает — рабочий каталог заморожен.

## Схема БД

Отдельным шагом схему больше не догоняют: это фаза B команды `cod-doc update`,
и идёт она до рестарта демонов. Ручной `cod-doc project migrate --all` остался
для случая, когда рантайм не трогают вовсе (например, после
`update --skip-migrate`).

Расхождение `alembic_version` с головой кода закрывает сессию
`SchemaMismatchError` — с ADO-188 одинаково и для hub-, и для embedded-записей
(веб отвечает 503 с подсказкой про миграции вместо стека SQLAlchemy). Прогон
после каждого обновления обязателен, а не гигиеничен: релиз приносит миграции,
которых в БД ещё нет.

Не гонять `alembic upgrade` из worktree по общей БД: миграция, которой нет в
main, делает базу нечитаемой для основного чекаута.

## Безопасность

Аутентификации у MCP-эндпоинта нет: `FastMCP` создаётся без
`auth_server_provider` и без `token_verifier`. Единственный контроль — bind на
`127.0.0.1`. Не выставлять порты наружу и не ставить `FASTMCP_HOST=0.0.0.0`.

Токен в заголовке клиента был бы театром — сервер его не проверяет.
