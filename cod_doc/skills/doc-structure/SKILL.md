# Skill — Структура дерева документации

## Когда подгружается

Импорт чужого репозитория, разбор Инбокса, переименование и слияние
документов, вопрос «куда это положить». Не подгружается ради правки прозы
внутри одного документа — это [doc-style](../doc-style/SKILL.md).

## Что здесь дерево

Хранимая сущность, а не вёрстка экрана: таблица `doc_node` (ключ, название,
`intent`, порядок, `parent_id`) плюс `document.node_id`. До ADO-116 дерево
строилось в вебе из `doc_key.split("/")`, то есть показывало файловую кучу: на
корпусе cod-doc это 14 папок `cod_doc/skills/*` с одним файлом внутри каждой и
узел `audit` на 42 документа.

Отсюда первое правило: **каталог на диске и раздел в дереве — разные вещи**.
Раскладка меняет `node_id` в БД и не двигает markdown. Файлы перекладывают
только по явной просьбе человека (инвариант `project-onboarding`).

## Роли разделов

| Раздел | Что лежит | Чего не лежит |
|---|---|---|
| `entry` | Навигаторы и точки входа: MASTER, README, гид контрибьютора | Всё, у чего есть свой раздел |
| `vision` | Зачем проект существует, для кого, чем ограничен | Как он устроен |
| `architecture` | Слои, границы, компоненты и их взаимодействие | Спека одного модуля |
| `data-model` | Сущности домена, схема, инварианты | Миграции как таковые |
| `capabilities` | Что система умеет — по способностям | Разбивка по модулям кода |
| `scenarios` | Наборы сценариев поведения | Вердикты покрытия — это доказательства producer'а |
| `standards` | Соглашения: код, документация, процесс | Разовые решения — это ADR |
| `skills` | Инструкции агенту, один документ на скилл | Документация для человека |
| `proposals` | RFC: контекст → предложение → миграция → риски | Уже принятые решения |
| `roadmap` | Приоритеты, милстоуны, планы исполнения | Отчёты о закрытии — это `audit` |
| `audit` | Отчёты, сверки, журналы | Всё, что будут перечитывать |
| `inbox` | Очередь разбора | Ничего надолго |

У каждого раздела есть `intent` — проза о том, что в нём лежит. Заводишь
раздел (`doc_node_create`) — пиши `intent`. Раздел без него превращается в
ярлык, и следующий разбор Инбокса снова упирается в «а куда это».

## Grooming после хаотичного импорта

Импорт зеркалит файловую кучу и ставит всему тип `module-spec` (дефолт
импортёра — на живом корпусе так помечено 46% документов). Разбирать это
надо явной фазой, а не «потом почистим».

1. **Засеять дерево:** `doc_tree_init` / `cod-doc doc tree init -p <slug>`.
   Идемпотентно, существующие ключи не трогает.
2. **Сухая раскладка:** `cod-doc doc tree classify -p <slug>`. Правила
   детерминированные (`services/doc_taxonomy.py`): конъюнкция условий внутри
   правила, побеждает первое совпадение. Посмотреть, что попало не туда, —
   дешевле, чем откатывать.
3. **Применить:** тот же вызов с `--apply`. По умолчанию трогает только
   неразложенное: повторный прогон не спорит с тем, что человек положил
   руками. `--all` перекладывает всё и перебивает ручную раскладку.
4. **Разобрать Инбокс.** Что осталось — спорно по существу, и это решение
   человека, а не правила. Типовые случаи: дубль (`specs/specs/modules` при
   живом `specs/modules`) — пометить `deprecated`; журнал сессии — в `audit`;
   документ чужого пакета — либо свой раздел, либо исключить из следующего
   импорта.
5. **Поправить типы.** Раздел лежит отдельно от типа: `module-spec` на всём
   корпусе — это не «плохо разложено», это «не проставлен жанр». Правится
   `doc_update` / `doc import` с честным frontmatter.
6. **Связать.** Документ без входящих ссылок выпал из навигации: на живом
   корпусе таких было 55 из 170. Смотри колонку «Связи» на экране
   документации — ноль слева подсвечен.

## Переименование и слияние

- `doc_rename` каскадом переписывает и строки `link`, и тела секций
  (`[[doc:OLD]]` → `[[doc:NEW]]`). Руками ссылки не чинят.
- Дубликаты не удаляют молча: младший помечается `deprecated` со ссылкой на
  живой, и только потом убирается — если убирается вообще.
- Удаление раздела с документами требует явного решения: либо `--reassign-to`,
  либо `--force`, который возвращает их в Инбокс. Молча растворить полку с
  документами нельзя.

## Критерии живого дерева

Не декларация: пять из шести считает `cod-doc doc tree health` (MCP —
`doc_node_health_get`), и он же пишет их в findings по `--sync`.

- Инбокс пуст. Пока он не пуст, корпус не разложен — это и есть его смысл.
  Проверяет рутина `doc_unplaced`; она про раскладку, health про наполненность.
- Ни один раздел не ниже своего `min_docs` — `NODE-THIN`.
- У каждого раздела заполнен `intent` — тот же `NODE-THIN`: пустой раздел без
  намерения даёт одну находку, а не две.
- Типы различают документы: доля самого частого выше 60% — `TREE-TYPES`.
  Обычно это дефолт импортёра, а не решение автора.
- Нет пачки безымянных `README`-сиблингов без роли: от трёх в одном разделе —
  `TREE-README`.
- Навигация замкнута: из `entry` достижимо всё, что должно читаться. Пока не
  считается автоматически — на живом корпусе недостижимы целые категории по
  своей природе (архив аудита, наборы сценариев, инструкции агенту), и одной
  цифрой это была бы неправда.

## Границы

- Вердикт «документация хорошая» этот скилл не выносит — только «разложена».
- Раскладку агент **предлагает**, человек подтверждает: предложения живут в
  `doc_node_suggestion` со статусом `pending`, как `link_suggestion`.
- Пробелы в содержании (чего вообще не написано) — `doc_node_health`:
  детерминированные правила выше плюс, отдельным проходом по кнопке, вердикт
  LLM «покрывают ли документы раздела его intent». Рутина LLM не зовёт.
