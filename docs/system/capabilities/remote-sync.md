# Capability — Remote Sync (облачное хранение и доступ)

> Проект COD-DOC живёт на нескольких машинах и у нескольких участников как
> набор равноправных реплик. Реплики обмениваются журналом операций через
> remote по модели git: `clone` / `pull` / `push`.

> ⚠️ **Намечено, реализовано частично (на 2026-10-17).** Спецификация по
> RFC 29 (принят 2026-10-11). Решения — ADR-016 (топология) и ADR-017
> (идентичность и захват операций), оба приняты. План `cloud-remote-2026-10`:
> секция A (идентичность и журнал) закрыта 2026-10-15
> ([аудит](../audit/2026-10-15-cloud-remote-section-a.md)), секция B
> (changeset, file-remote, push/pull) — 2026-10-17
> ([аудит](../audit/2026-10-17-cloud-remote-section-b.md)), секция C (слияние
> и конфликты) — 2026-10-17
> ([аудит](../audit/2026-10-17-cloud-remote-section-c.md)), секции D–F не
> начаты. Работает только `file://` remote; pull сливает офлайн-правки
> по правилам §3.7, несведённое — в `sync_conflict`. `clone`, аренды номеров и
> checkout'а нет. Контракт ниже — цель; детали схемы и протокола — в
> [RFC 29](../../../proposals/29-cloud-remote-sync.md).

## 0. As implemented (2026-10-17)

Секция A плана (CLO-001…009) — фундамент репликации внутри одной БД:

- **Реестр классов** `cod_doc/infra/sync_registry.py`: каждая таблица — ровно
  один класс из §3 (authored / journal / derived / local), уезжающие колонки
  перечислены явно, restricted и машинные пути — fail-closed.
- **Идентичность** (миграция `0049_sync_identity`): колонка `uid` во всех
  authored-таблицах, кроме тег-таблиц с составным PK; шесть служебных таблиц
  (`replica`, `sync_op`, `changeset`, `sync_ref`, `sync_lease`,
  `entity_alias`). Схема — [DATA_MODEL §3.18](../DATA_MODEL.md).
- **Порядок** (миграция `0050_sync_rank`): дробный ранг `rank`/`node_rank` в 11
  местах порядка; `position` стал локальным производным.
- **Журнал**: хук на фабрике сессий (`cod_doc/infra/sync_capture.py`) пишет
  операцию `sync_op` на каждую запись в authored-данные — с HLC своей реплики,
  автором и только уезжающими полями. Журнал копится всегда, даже без remote.

Секция B (CLO-010…016, [аудит](../audit/2026-10-17-cloud-remote-section-b.md))
— обмен между репликами через `file://` remote:

- **Changeset v1** (`sync_service/changeset.py`): каноническая форма §10.4,
  адрес — sha256, на проводе `CDC1` + zstd; объект с remote разбирается как
  недоверенный вход (`SYNC-102`).
- **`FileRemote`** (`cod_doc/infra/remote/file.py`): CAS ref'ов под `flock`,
  спуск по каталогу `openat`/`O_NOFOLLOW`, потолки чтения.
- **`push`**: упаковка хвоста журнала в один changeset, CAS `refs/main` только
  когда remote на локальной голове, до трёх повторов через pull, дальше
  `SYNC-103`.
- **`pull`**: только fast-forward; changeset проверяется до первой записи
  (схема — `SYNC-104`, проект, уезжающие поля, штампы HLC, каскад в restricted)
  и применяется своей транзакцией. Правка той же сущности на обеих сторонах
  в секции B давала `MergeRequiredError`; с секции C — слияние (ниже).
- **Дайджест и `verify`**: sha256 уезжающего состояния проекта без `row_id`,
  `position`, restricted и journal; две реплики после fast-forward равны.
- **Поверхности**: CLI `cod-doc remote add|list|remove`, `fetch`, `pull
  [--dry-run]`, `push [--no-retry]`, `sync status [--verify]|log|verify`; MCP
  `sync_status`, `sync_pull`, `sync_push` (профили `standard`/`full`).

Секция C (CLO-017…027, [аудит](../audit/2026-10-17-cloud-remote-section-c.md))
— слияние вместо `MergeRequiredError`:

- **Pull сливает свой хвост с чужими changeset'ами** (`sync_service/merge.py`):
  поле существующей строки — LWW по штампу `(hlc, op_id)`, равные значения
  поглощаются; `rank` — обычное поле, ничью решает `uid`. Merge-changeset не
  строится: разрешившие расхождение операции уезжают следующим push'ем.
- **Стратегии по виду случая:** текст (`text_columns`: описания, тела секций,
  решения ADR) — diff3 построчно от общего предка; `task.status` — больший
  штамп только при допустимом переходе `ALLOWED_TRANSITIONS`, двойной офлайн-
  checkout — конфликт `double_checkout`; рёбра и тег-связи — add-wins;
  удаление против правки — удаление выигрывает, правка — в конфликт
  `delete_edit` со снимком поддерева; совпавший натуральный ключ — склейка в
  одну строку (`entity_alias reason=merged`), буква секции плана —
  перебуквление.
- **Ревизии уезжают** (`sync_service/journal.py`): объединение по
  `revision_id`, родитель — локальная голова; ревизия уезжает, только если её
  сущность уезжает целиком. Лента `activity_event` остаётся на реплике.
- **Конфликты** — local-таблица `sync_conflict`; CLI `cod-doc sync conflicts`
  / `sync resolve <uid> --take ours|theirs|--text-file`, MCP `sync_conflicts`
  / `sync_resolve`, пункт `sync_conflict` в `curator_next` (ранг 4, выше
  реестра хэшей). Разрешение — обычная запись, она уезжает следующим push'ем.
- **Сходимость** (`tests/services/sync/test_convergence.py`, SCN-087): три
  реплики со случайными пересекающимися офлайн-правками всех видов в любой
  перестановке push/pull после разрешения конфликтов приходят к одному
  дайджесту; множество подписей открытых конфликтов от перестановки не
  зависит.

Чего нет: `clone` (CLO-029) — вторая реплика заводится эмуляцией (рецепт —
[аудит секции B §8](../audit/2026-10-17-cloud-remote-section-b.md)); S3 и умный
remote (`SYNC-110` до CLO-028/035); разрешение `double_checkout` (CLO-031);
двойники арендованных номеров `task_id`/`adr_id`/… (`MergeRequiredError`,
CLO-030); перенос хвоста на переписанную историю remote (CLO-032);
аутентификация ни в REST API, ни в MCP (секция E).

## 1. Зачем

Три случая, которые сегодня не закрыты ничем:

1. **Владелец на нескольких машинах.** Ноутбук и десктоп правят один проект, в
   том числе без сети, и ни одна правка не теряется.
2. **Небольшая команда.** Участник получает проект по токену с ролью и видит
   чужие изменения после `pull`. Параллельная правка не затирает чужую молча.
3. **Бэкап.** Любой remote хранит полную историю; после потери диска проект
   восстанавливается через `cod-doc clone`.

Облачный ИИ-клиент (VISION §6 п. 5) — частный случай второго: он работает
против серверной реплики через remote MCP со своим агентским токеном.

## 2. Модель

| Понятие | Что это |
|---|---|
| реплика | полная локальная SQLite проекта; у сервера такая же |
| операция (`sync_op`) | изменение полей одной сущности: новые значения и значения-предки, HLC, автор |
| changeset | неизменяемый пакет операций с родителями; адрес — sha256 |
| remote | хранилище changeset'ов и `refs/main` проекта: `file://`, `s3://` (MinIO/S3) или `https://` (`cod-doc serve`) |
| конфликт | строка `sync_conflict`: поле, «наше», «их», предок |

**Что синхронизируется.** Реестр классов данных (ADR-017):

- `authored` — документы, секции, задачи, планы, истории, ADR, сценарии и связи
  между ними — уезжают операциями;
- `journal` — ревизии и activity — объединяются по глобальному ID;
- `derived` — ссылки, FTS, structure, routine-находки — пересобираются
  локально;
- `local` — прогоны, трассы, хэши рабочего дерева, вычисляемый `position`, а
  также документы `sensitivity = restricted` с их секциями — не уезжают никогда.

Порядок элементов держит синхронизируемый дробный `rank`, а не целый `position`.

Markdown-проекции не синхронизируются: их везёт git репозитория. Два канала
независимы: одинаковые значения, приехавшие и через git, и через remote,
сливаются без конфликта. В синхронизируемом проекте правки идут через БД, а
`doc import` — только для новых файлов и инициализации.

**Слияние** при `pull` детерминировано:

- поля сливаются LWW по HLC, равные значения поглощаются;
- тексты — 3-way merge от предка;
- статус задачи проверяется статус-машиной;
- множества работают по правилу add-wins;
- совпавшее имя-смысл (`doc_key`, якорь секции, раздел дерева, рутина)
  склеивается в одну сущность, совпавшая буква секции плана перебуквляется;
- delete побеждает edit: одна операция удаления родителя, поддерево сносит
  каскад БД, правка под удалённым родителем уходит в конфликт со снимком;
- чужие ревизии встают поверх локальной головы с общими `revision_id`.

Неразрешимое уходит в `sync_conflict`, а в БД остаётся локальная версия.

**Схема.** Миграция, меняющая authored-колонки, открывает эпоху: перед ней
`cod-doc update` требует `push`, после неё remote получает снапшот новой эпохи.

## 3. Контракт поверхностей

| Действие | CLI | MCP (`standard`/`full`) |
|---|---|---|
| подключить remote | `cod-doc remote add <name> <url>`, `remote login <name>` | — |
| получить проект | `cod-doc clone <url> [--project <slug>] [<dir>]` | — |
| обменяться | `cod-doc pull -p <slug>`, `cod-doc push -p <slug>` | `sync_pull`, `sync_push` |
| состояние | `cod-doc sync status -p <slug>` | `sync_status` |
| конфликты | `cod-doc sync conflicts`, `sync resolve <uid> --take ours\|theirs\|<текст>` | `sync_conflicts`, `sync_resolve` |
| сходимость | `cod-doc sync verify` | `sync_status(verify=True)` |
| захват задачи | `cod-doc task checkout <id> [--offline]` | `task_checkout(offline=…)` — при remote замок через CAS |
| после пропущенной эпохи | `cod-doc sync export-pending` | — |
| доступ (умный remote) | `cod-doc member add/list/remove`, `cod-doc token create/revoke` | — (намеренно) |

Профиль `agent` новых тулов не получает: открытые конфликты и отставание от
remote куратор видит пунктом очереди `curator_next`. Автосинк — рутина `sync`.

## 4. Доступ

| Remote | Кто пускает | Разграничение |
|---|---|---|
| `file://`, `s3://` | права ФС / S3-креды | нет: один владелец или доверенная группа |
| `https://` (`cod-doc serve`) | Bearer-токен (sha256 на сервере, отзываемый, на устройство или агента) | роль на проект: reader (fetch), writer (+ push, аренда ID), admin (+ участники, токены) |

Умный remote штампует changeset аутентифицированным actor'ом и отвергает
операции с чужим `author`. Агентский actor принадлежит человеку и не
получает роль выше его.

**Развёртывание.** `cod-doc serve` слушает loopback; наружу его выставляет
reverse proxy (Caddy) с TLS на 443. Сервер ограничивает частоту запросов и пишет
отказы аутентификации в журнал. Встроенного TLS и VPN-only режима нет.

**Секреты.** Документы `restricted` не покидают реплику ни на каком remote;
`confidential` и ниже синхронизируются — их аудитория совпадает с участниками
проекта.

## 5. Инварианты

- Две реплики, применившие одно множество changeset'ов, имеют один дайджест
  `authored`-данных (`sync verify`).
- Push только fast-forward: изменение, не видевшее чужой push, отвергается, а
  не перезаписывает его.
- Два постоянных человеческих ID не совпадают никогда: номера выдаются из
  непересекающихся арендованных блоков.
- Реплика не применяет changeset со схемой новее своей.
- Каждая запись в authored-данные проходит через `Session` и попадает в
  журнал: bulk-запись в authored-таблицы запрещена гейтом.
- Одно имя-смысл — одна сущность на всех репликах после слияния.
- Параллельные вставки в упорядоченный список не меняют порядок остальных
  элементов.
- При настроенном remote одну задачу держит не больше одного онлайн-замка.
- Строка `restricted`-документа не попадает ни в один changeset.
- Changeset прошлой эпохи не применяется к реплике новой эпохи.

## 6. Non-goals

- Ветки и PR-flow внутри БД; realtime и посимвольные CRDT.
- Multi-tenant, SaaS, регистрация, организации (proposals/README).
- Синхронизация derived-данных и markdown.
- E2E-шифрование, partial clone, P2P без remote, подписи changeset'ов (v1).
- Права ниже проекта (на документ / sensitivity) — ARCHITECTURE §12.3.

## 7. Acceptance (capability-level)

- [ ] Две реплики с одного `s3://`-remote правят одну задачу офлайн (разные
      поля) и после `pull`/`push` сходятся без конфликта.
- [ ] Пересекающаяся правка одной секции даёт ровно один `sync_conflict`,
      видимый в `curator_next`; после `sync resolve` дайджесты совпадают.
- [ ] Задачи, созданные офлайн на двух репликах, получают непересекающиеся
      постоянные номера; провизорные имена резолвятся через алиас.
- [ ] `cod-doc clone` на чистой машине восстанавливает проект до дайджеста
      remote.
- [ ] На умном remote токен reader получает отказ на push; changeset с чужим
      `author` отвергается.
- [ ] Две реплики создали секцию с одним заголовком в одном документе — после
      обмена секция одна, второй `uid` резолвится через алиас.
- [ ] Удаление документа на одной реплике и правка его секции на другой дают
      один конфликт, из которого документ восстанавливается.
- [ ] Второй `task_checkout` задачи при настроенном remote получает отказ до
      начала работы.
- [ ] `restricted`-документ после `push` отсутствует на remote.
