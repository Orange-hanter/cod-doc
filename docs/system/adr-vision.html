ADR System — Видение и концепции интеграции

First-class реестр архитектурных решений с автонумерацией, supersede-DAG, визуальным редактором и Mermaid-графом. Документ описывает не «что писать в коде», а как ADR-сущность должна жить в существующей экосистеме COD-DOC, какие альтернативы я взвешивал и какие предложения по интеграции хочу зафиксировать перед стартом реализации.

TL;DR

Реализуем capability adr-system в три фазы: Domain & MCP (модель, сервис, 9 MCP-тулов, CLI) → Web UI (список / редактор с live-Mermaid / detail / supersede-граф) → Migration (шаблон + перенос 5 ADR из arch/architecture.md §3). Ключевое решение, требующее твоего апрува: как соотносить новую сущность ADR с уже специфицированной Decision из decisions-and-questions — три варианта, рекомендация в §9. Никакого кода до апрува не пишу.

1. Зачем сейчас

Архитектурные решения в COD-DOC живут разрознено:

  • arch/architecture.md §3 — пять ADR в markdown-таблице, без статуса/supersede.
  • proposals/*.md — RFC-стиль; решения по ним фиксируются ad-hoc.
  • Audit-отчёты в docs/system/audit/ — обоснование разовых решений (например, validation-pattern).
  • Commit-сообщения — контекст теряется через 3–6 месяцев.

Боль:

  • Нет единого реестра «какое решение принято, когда, кем».
  • Невозможно отследить supersede-цепочку («ADR-005 заменён ADR-012, который частично откатывает ADR-003»).
  • У авторов нет визуального инструмента — markdown-таблицы и Mermaid-блоки приходится размечать руками.
  • Агент, принимающий решение, не имеет «слота» куда его записать — оно теряется в commit-меседже.

3. Доменная модель

Чистый dataclass в cod_doc/domain/entities.py, без зависимости от инфраструктуры:

@dataclass(slots=True)
class Adr:
    project_id: int
    adr_id: str                       # ADR-NNN, autonumbered per project
    title: str
    status: AdrStatus                 # PROPOSED | ACCEPTED | DEPRECATED | SUPERSEDED
    context: str                      # markdown
    decision: str                     # markdown
    consequences: str                 # markdown
    decided_by: str                   # human:<email> | agent:<run-id>
    decided_at: datetime
    row_id: int | None = None
    superseded_by: str | None = None  # ADR-id, заменивший этот
    created: datetime | None = None
    last_updated: datetime | None = None

Отдельные сущности для рёбер графа:

AdrDiagram

0..N Mermaid-блоков с подписью. adr_id FK + position + mermaid_source + caption. Render через client-side Mermaid.js (тот же, что для plan-graphs).

AdrSupersedes

Ребро from_adr_id → to_adr_id + reason. DAG, цикл отвергается на write-path.

AdrTask

ADR может предписывать задачи: adr_id ↔ task_id. Полезно для «эта задача — следствие ADR-007».

AdrLink (новый)

Полиморфная связь ADR ↔ Document/Module/Story. Параллель StoryLink. Альтернатива — переиспользовать Link с LinkKind.ADR; см. §5.

Где это в инфре

  • SQLA-модели — cod_doc/infra/models/adr.py (4 таблицы).
  • Migration — 20260514_0017_adr_tables.py (Alembic).
  • Repository — cod_doc/infra/repositories/adr_repo.py с методами под autonumber + cycle-check.
  • Service — cod_doc/services/adr_service/ (пакет, по примеру story_service/).

4. Lifecycle статусов

PROPOSED ─ accept ─▶ ACCEPTED ─ supersede ─▶ SUPERSEDED
PROPOSED ─ reject ─▶ DEPRECATED или ACCEPTED ─ deprecate ─▶ DEPRECATED

Инварианты

  • PROPOSED мутируется свободно (тело редактируемое).
  • ACCEPTED делается immutable: context/decision/consequences править нельзя; добавление diagram — да, изменение title — нет. Только supersede/deprecate.
  • SUPERSEDED — следствие записи ребра adr_supersedes: статус выставляется сервисом транзакционно, не вручную.
  • DEPRECATED — терминал, обратного пути нет (новый ADR — это новый ID, не «revive»).
Альтернатива. Не делать ACCEPTED immutable, а полагаться на revision-history. Контраргумент: ACCEPTED-ADR — обещание системе, его слом без следа в supersede-графе ломает «обоснованность решений». Immutable + supersede строже и эксплицитнее.

5. Карта интеграций

ADR — не остров: он касается почти каждой существующей capability. Ниже — точки соприкосновения и моё предложение по каждой.

5.1 Revision history

Добавляем EntityKind.ADR. Все мутации (create / update / supersede / deprecate / add_diagram / link_task) пишут revision через revision_service.write() — единый паттерн с doc/task/story. Бонус: revision_revert из коробки откатывает ADR.

5.2 Auto-linking

Добавляем LinkKind.ADR и резолвер для [[ADR-NNN]] / [ADR-NNN]. Любой markdown в проекте (план, спека, task-doc) автоматически получает кликабельную ссылку на ADR. Стейл-линки (битые ID) ловятся link_verify.

Рекомендация. Реализовать парсинг паттерна ADR-\d{3,} отдельным правилом — он короткий и не пересекается с задачами (COD-NNN) или сторями (US-NNN).

5.3 Tasks

adr_link_task(adr_id, task_id) создаёт ребро «эта задача — следствие ADR». В Web-странице задачи появляется чип «ADR-007 Use SQLite by default» как hover-tooltip с decision-полем.

5.4 Stories

User Story связывается с ADR в одну сторону: «story ставит вопрос → ADR его закрывает». Реализация — через существующий StoryLink с новым StoryLinkKind.ADR, либо через симметричный adr_link_story(). Я бы выбрал второй вариант: меньше развилок в существующем story-сервисе.

5.5 Modules / specs

ADR может затрагивать модуль (cod_doc/domain, services/plan_service и т.д.). Поле affects_modules: list[str] в ADR + индекс в adr_link. На странице capability/module появляется блок «ADRs, governing this module» — это даёт читателю быстрый context.

5.6 Plans

Execution-plan может декларировать «implements ADR-007, ADR-009». plan_audit добавляет правило: если плановая задача меняет файл в модуле, охваченном ACCEPTED-ADR, и нет линка task↔adr — warning.

5.7 Approvals

Переход PROPOSED → ACCEPTED опционально требует approval_request (configurable per project). Удобно, когда ADR пишет агент: оно лежит как proposal, человек кликает «accept», approval-service делает резолв.

5.8 Activity log

Каждое мутирующее действие на ADR публикует ActivityEvent(kind=ADR_*) через activity_service. В web-странице runs/activity появляется человекочитаемая лента.

5.9 Routines

Новая рутина adr-stale: ADR в PROPOSED > 14 дней → warning. Другая — adr-orphan: ACCEPTED ADR без единого task↔adr или doc↔adr ребра.

5.10 Skills / agents

Новый skill adr-author — гайд для LLM-агента: «когда писать ADR (≥2 модуля задеты или меняется схема БД), что в Context vs Decision vs Consequences, как формулировать supersede».

5.11 Context retrieval (Snowball)

L1-контекст агента получает список ACCEPTED-ADR проекта (id+title+1-line context). L2 подгружает тело конкретного ADR по id. Не загружаем DEPRECATED по умолчанию.

5.12 Templates

Default templates/adr_default.md.j2. Per-project override: <project>/templates/adr.md.j2. Web-форма — визуальное представление этого шаблона: одно изменение схемы шаблона → автоматически в форме (через введение field-описателя поверх Jinja).

5.13 Search / projections

ADR проецируется в markdown (под docs/adr/ADR-NNN.md) для git-видимости и индексируется в ChromaDB через существующий projection_service. Semantic-search «найди ADR про PostgreSQL» работает «из коробки».

7. Концепция визуального редактора

Главное различие ADR от прочих markdown-документов в COD-DOC — структурированный шаблон. Это даёт нам право не показывать сырой markdown, а сделать форму с предпросмотром.

Левая колонка — форма

  • Title (input)
  • Context (textarea, markdown)
  • Decision (textarea)
  • Consequences (textarea)
  • Diagrams (1..N Mermaid-блоков с inline-preview)
  • Supersedes (multi-select из ACCEPTED ADR)
  • Affects modules / files (combobox)

Правая колонка — preview

  • Server-side markdown render (тот же cod_doc/api/web/markdown.py)
  • Mermaid через клиентский mermaid.js (уже в проекте для plan-graph)
  • Live-debounce 300 мс, обновление через HTMX-fragment
  • Badge с целевым статусом (PROPOSED по умолчанию)

UI-инварианты

  • Supersede-form не позволяет выбрать себя или создать цикл — серверная проверка перед сохранением.
  • Mermaid с синтаксической ошибкой → блок не сохраняется (валидатор на стороне сервера через subprocess или mermaid-cli; если тяжело — fallback: сохраняем как есть, помечаем render_status=error).
  • «Save as PROPOSED» (draft) vs «Save & Accept» (один клик). Второй требует подтверждения, поднимает approval, если включён.
Альтернатива №1 — WYSIWYG-редактор (TipTap/ProseMirror). Контраргумент: COD-DOC хранит markdown канонично; WYSIWYG усложняет roundtrip и indexing. Откладываем.
Альтернатива №2 — single big textarea с server-side парсингом разделов. Хуже UX (нет live-preview по секциям), легко сломать формат. Не делаем.

8. Граф решений

Граф supersede — главная визуальная фича. Он же — диагностический инструмент: если у тебя 30 ADR и 12 SUPERSEDED-цепочек, граф мгновенно показывает «зрелые» области и «горячие» (где решения постоянно переписываются).

Эволюции (не MVP, но проектируем под них)

  • Layered view: ADR → Modules → Tasks → Documents. Один граф, четыре уровня. Полезно для «impact» — нажал на ADR, увидел всё, что от него зависит.
  • Timeline view: ADR по оси X = время, цветом — статус. Видно, когда система входила в фазы пересмотра.
  • Coverage view: матрица «модули × ADR» — какие модули регулируются, какие нет (≈ aerial-view технического долга).

9. Развилка ADR ↔ Decision (требует апрува)

В docs/system/capabilities/decisions-and-questions.md уже есть сущность Decision (DEC-NNN) со схожей семантикой (status, context, decision, consequences, supersedes). adr-system ввёл вторую сущность Adr (ADR-NNN) с почти тем же набором полей.

Это коллизия, и её надо разрешить до миграции, а не после. Три варианта:

A. ADR есть Decision (рекомендую)

Сливаем сущности. Реализуем как Adr с префиксом ADR-NNN. Capability decisions-and-questions упрощается: «Decisions = ADR system», «Open Questions» — остаётся отдельной мелкой сущностью.

Плюсы: одна модель, одна страница, одна история. Меньше путаницы у пользователя.

Минусы: нужно обновить decisions-and-questions.md; это лёгкое.

B. ADR — это tech, DEC — product

Параллельные сущности с разной семантикой: ADR — техрешения, DEC — продуктовые / процессные. Префиксы разные.

Плюсы: разделение по уровню абстракции, как в Restate.

Минусы: две модели, две UI-страницы, два MCP-набора. На малом проекте — оверкилл.

C. Дроп decisions-and-questions

Удаляем capability как нереализованную. ADR закрывает всю функциональность, кроме OpenQuestion — её выносим в отдельный thin-capability «open-questions» (или присоединяем к ADR как «PROPOSED без decision»).

Плюсы: самая чистая декомпозиция.

Минусы: требует ревизии MASTER.md и нескольких докстрингов.

Моя рекомендация — A с уклоном в C. ADR-сущность становится реализацией «Decision»; capability decisions-and-questions переписывается так, чтобы её «Decision» ссылалась на adr-system, а OpenQuestion остаётся отдельной маленькой сущностью (это тот случай, когда вопросы и решения — действительно разные графы). Префикс — ADR-NNN, не DEC-NNN (короче, общепринят).

11. Открытые вопросы (на твою сторону)

  1. ADR vs Decision — какой из трёх вариантов §9 выбираем?
  2. Approval gating — делаем PROPOSED → ACCEPTED опциональным через approvals (рекомендую да, опционально, выключено по умолчанию)?
  3. Markdown projection — генерируем ли docs/adr/ADR-NNN.md для git-видимости, или ADR живёт только в БД + Web UI? Я бы делал — это «free» semantic-search и diff в PR.
  4. Server-side Mermaid validation — допустимо ли поставить mermaid-cli в Dockerfile, или валидируем только клиентом и принимаем риск битых блоков?
  5. Префикс ID — фиксируем ADR- (общепринят) или хотим что-то проектно-специфичное?
  6. Authorship для агентов — формат agent:<run-id> ок? Это даст возможность кликнуть в decided_by и попасть на страницу run-а.

12. Риски и митигации

Риск 1. Двойная сущность ADR/Decision создаст user-confusion. Митигация: закрыть §9 до Phase 1.
Риск 2. Cycle-detection становится дорогой на больших проектах (DFS по adr_supersedes). Митигация: вероятный размер — десятки, не тысячи. DFS in-memory ок до 10⁴ узлов.
Риск 3. Mermaid live-preview лагает в браузере для больших диаграмм. Митигация: render debounce 300мс + лимит ≤200 строк на блок.
Риск 4. Autonumber race при concurrent create. Митигация: SELECT FOR UPDATE на row проекта или advisory lock; либо UNIQUE(project_id, adr_id) + retry-on-conflict.
Риск 5. Шаблон ADR через 2 года перестанет влезать в три textarea (захочется доп. полей: «Alternatives», «Rollback»). Митигация: хранить в БД typed body (context, decision, consequences) и extra: JSON для расширений без миграции.

13. Что оставляем на потом

  • Voting / quorum — ADR в COD-DOC принимает один человек или агент; полноценный RFC-процесс не нужен.
  • Comment-threads — обсуждение идёт во внешнем issue-tracker.
  • Auto-suggest «нужен ADR здесь» — соблазнительно, но шумно. Лучше через skill adr-author, чем через автодетектор.
  • Cross-project ADR — multi-project поле shared_with. Пока — per-project, замкнуто.
  • Diff между ADR-revisions в UI — пока через generic revision_get.
  • Эмбеддинги «similar ADRs» — поверх ChromaDB-проекций. Easy add-on, не MVP.
