# Audit — Plan `cloud-remote-2026-10`, Section C closure («Слияние и конфликты»)

> **Контекст.** [RFC 29](../../../proposals/29-cloud-remote-sync.md) §11.2,
> секция C: pull, у которого свой неупакованный хвост и чужие changeset'ы
> трогают одно и то же, больше не останавливается на `MergeRequiredError`, а
> сливает их по таблице правил §3.7; то, что слияние не свело само, ложится в
> `sync_conflict` и решается человеком. Аренда номеров и checkout'а, clone и
> S3 — секция D.

## 1. TL;DR

Секция C закрыта по коду: 11/11 задач (CLO-017…027) в `main` пятью PR (#224,
#225, #226, #227 и этот PR). CI на коммитах слияния первых четырёх
зелёный. Одна миграция — `0051_sync_conflict`. Новые поверхности:
`cod-doc sync conflicts` / `sync resolve`, MCP `sync_conflicts` /
`sync_resolve`, пункт `sync_conflict` в `curator_next`.

Property-тест CLO-027 (три реплики, все виды правок, случайные перестановки
push/pull) нашёл десять расхождений в коде секции; все исправлены в этом PR с
регрессионным тестом каждое (§6.2). Там же исправлен `sync verify` у
приёмников проекта с придержанными колонками: дайджест владельца не
воспроизводился приёмником, на `main` это воспроизводится (§6.3). Буква acceptance CLO-027 выполнена с двумя
оговорками, обе — следствие того, что `sync_conflict` local (§4.1).

Что не сходится и переходит дальше: `double_checkout` (CLO-031), двойники
арендованных номеров (CLO-030), история remote, переписанная без локальной
головы (CLO-032), закрытие конфликта на второй реплике после разрешения на
первой (§7).

## 3. Что построено, по стратегиям

| Случай | Модуль | Правило | Конфликт |
|---|---|---|---|
| скалярное поле существующей строки | `merge.lww` | больший штамп `(hlc, op_id)`; HLC — `<ms>.<counter>.<replica_uid>` фиксированной ширины, ничью по времени решает uid реплики; одно значение с двух сторон поглощается (поле уходит из хвоста, операции нет) | нет |
| порядок (`rank`) | `merge.lww` | обычное поле; равные ранги упорядочивает `uid` | нет |
| текст (`text_columns`) | `text_merge` | diff3 построчно от `base` **первой** своей записи поля; непересекающиеся ханки сливаются, сведённое уходит со свежим штампом (D3) | `text`, в БД — «наше» |
| `task.status`, `checked_out_*` | `status_merge` | больший штамп, только если переход допустим по `ALLOWED_TRANSITIONS`; legacy-написание того же bucket'а — LWW | `status`; оба взяли свободный замок — `double_checkout` |
| удаление ребра против его записи | `set_merge` | add-wins: сливающая реплика пишет ребро заново одной вставкой всех полей | нет |
| удаление против правки, FK на удалённое | `tombstone` | удаление выигрывает; поддерево снимается в конфликт (с правками хвоста), операции хвоста над ним убираются | `delete_edit`, `theirs` = снимок `{root, rows}` |
| совпал натуральный ключ при вставке | `keys` | выживает меньший `(hlc создания, uid)`; поля — LWW по последней записи; проигравший uid — `entity_alias`; метка (`plan_section.letter`) — следующая свободная буква | `key_merge` при разных телах `text_columns` |

**Устройство ядра.** Локальная голова — всегда предок головы remote:
changeset появляется только после CAS. Поэтому merge-changeset не строится —
операции, разрешившие расхождение, ложатся в хвост и уезжают следующим push'ем
(B12). `merge.check` до первой записи pull'а проверяет, есть ли стратегия у
каждого случая; исключение — совпадение ключа, его видно только запросом при
вставке, и его граница срабатывает внутри транзакции changeset'а.
`Context.retract` снимает конфликт промежуточной записи поля, если тот же
changeset пишет поле ещё раз (D9).

**Разрешение** (`conflicts.resolve_conflict`) — обычная запись одной
транзакцией: значение через ORM (захват пишет операцию со свежим HLC; если
значение уже в БД — явный `sync_capture.record`), ревизия сущности, событие
`sync.conflict_resolved`, отметка `resolved`. `--take theirs` у `delete_edit`
пересоздаёт поддерево с исходными uid (`apply.restore_rows`); строка снимка с
пометкой `partial` (сущность родилась до журнала) — `SYNC-301` до записи.

### 4.1 Acceptance CLO-027 — что проверено и чем это отличается от буквы

Acceptance: «три реплики с пересекающимися офлайн-правками в любой
перестановке pull/push приходят к одному дайджесту и одному множеству
открытых конфликтов по uid».

**Прогон.** Реплики A, B, C и `FileRemote` в tmp. Два раунда; в каждом
каждая реплика делает 2–5 случайных правок из 19 видов: LWW-поля (`title`,
`priority`), текст (`task.description`, тела секций), статус через ORM (любая
пара значений), checkout/release, ребро `dependency` (добавить, снять,
`note`), тег-связь (поставить/снять), вставка шага сценария по рангу,
удаление документа против правок его секций, двойники ключа (документ,
секция, тег, буква секции плана), новая задача, сценарий на restricted-
документе своей реплики (ссылка и `group_key` придержаны) и правка заголовка
любого сценария с любой реплики. Затем картина копируется в
три вселенные, и в каждой — своя случайная перестановка: 14 случайных
`push`/`pull` (push без повтора, отказ CAS — тоже шаг), потом круги
`pull`+`push` до затихания (хвостов нет, три головы = голова remote). Сиды
параметризованы: 8 по умолчанию (~20 с), `CLO027_SEEDS=N` расширяет; перед PR
прогнано 500 сидов × 2 раунда × 3 вселенные без падений (после фикса F8 и
расширения генератора — заново). На первых 40 сидах слияние открывало
конфликты всех видов, кроме исключённого `double_checkout`: `key_merge` — 38
раз (в 5 сидах), `delete_edit` — 18 (5), `status` — 12 (4), `text` — 12 (4);
сценариев на restricted-документе заведено 26.

**Отличия от буквы.**

1. *Дайджест — после разрешения конфликтов.* Конфликт оставляет в БД «наше»
   (§3.7), реплика держит своё значение поля, пока человек не решит (D1). До
   разрешения три реплики законно расходятся в полях открытых конфликтов.
   Тест разрешает все открытые конфликты на каждой реплике (`take`
   выводится из подписи, одинаково во всех вселенных), снова доводит до
   затихания и повторяет до пустого списка (с CLO-045 — каждую подпись на
   одной реплике, остальные закрывает маркер, C37); затем требует один полный
   дайджест (вместе с журналом ревизий), `sync verify` = remote и построчно
   равное уезжающее состояние.
2. *Множество конфликтов — по подписи, не по uid.* `sync_conflict` — local
   (§3.2): конфликт открывает реплика, сливавшая свой хвост, с uuid7 своей
   генерации. «Одно множество по uid» у трёх реплик недостижимо по
   построению. Сравнивается множество подписей `(entity_kind, entity_uid,
   field, kind)`, объединённое по трём репликам в момент затихания: оно
   одинаково во всех вселенных одного сида. По репликам внутри вселенной
   множества разные: кто открыл, зависит от того, кто сливал.
3. Генератор не порождает `double_checkout` (checkout в раунде делает одна
   реплика) и двойников арендованных номеров: первое не сходится до CLO-031
   (D6), второе — `MergeRequiredError(CLO-030)`. ~~Статус одной задачи в раунде
   пишут не больше двух реплик, по разу каждая: у трёх записей множество
   конфликтов `status` зависит от порядка (F11).~~ Снято в CLO-044 (C36):
   статус пишут любые реплики любое число раз.

SCN-087 «как написан» (pull+push на A, B, C; pull, пока приходит новое;
`verify` на каждой) — отдельный детерминированный тест без конфликтов:
одинаковые дайджесты и пустые множества конфликтов.

### 6.3 Дайджест проекта с придержанными колонками (F8)

**Симптом.** Сценарий на restricted-документе уезжает без `document_id`,
`doc_key`, `section_anchor`, `doc_content_hash` (секция A) и `group_key` (этот
PR). У приёмника эти колонки — `NULL` и заглушка `restricted`. Владелец не
включал придержанные колонки в строку дайджеста, приёмник включал то, что у
него лежит: дайджест владельца ≠ дайджесту приёмников, а `sync verify`
сверяет с дайджестом remote, который пишет push владельца. Итог: `verify`
равен у владельца и не равен у **каждого** приёмника любого проекта с
придержанной ссылкой.

**На `main` до этого PR воспроизводится** (дерево `origin/main` = `9c16074`,
явный `group_key="g"`): `verify` A — `True`, B — `False`, C — `False`.

**Решение.** Дайджест хеширует то, что приёмник может воспроизвести:
придержанная колонка входит в строку дайджеста у владельца значением, которое
окажется у приёмника, — `NULL` или `sync_registry.WITHHELD_FILL`
(`sync_capture._shipped_line`). Приёмнику знать о придержании не нужно: он
хеширует строку как есть. Маркер в changeset'е не понадобился — значение
приёмника детерминировано реестром. Гейт
`test_every_withheld_not_null_column_has_a_receiver_fill` требует заглушку у
каждой придержанной NOT NULL-колонки.

**Проверка.** `test_withheld_columns_hash_the_same_on_owner_and_receivers`
(`group_key` по умолчанию и явный): `verify` равен на всех трёх, в том числе
после правки чужого сценария приёмником. Red-before — `AssertionError: b`
(`VerifyResult(… equal=False)` у первого приёмника). Генератор property-теста
дополнен сценариями на restricted-документе и правкой их заголовка;
сравнение состояния в тесте идёт по строкам дайджеста (`shipped_state` →
`digest._line`), а не по `shipped_fields`, у которых у владельца законно нет
придержанных колонок.

Было: проверка статуса попарная (CLO-020): у трёх записей статуса одной задачи (три реплики или две записи одной — сид 25: backlog A против cancelled → review B) промежуточная запись может проиграть допустимым переходом и не уехать (blocked A → in_progress B → done C: B принимает done и обрезает свой in_progress), а C судит blocked → done напрямую и открывает `status`. В порядке, где in_progress приходит к C первым, конфликта нет. Дайджест после разрешения сходится, расходится только множество конфликтов. Найдено property-тестом (сиды 386, 25, 12); генератор ограничен двумя писателями статуса задачи на раунд, по записи на каждого. Закрытие конфликта поздней чужой записью поля между changeset'ами (продолжение `retract`, D9) этот случай не лечит: in_progress до C не доезжает | RFC §3.7: правило статуса по множеству записей, а не по паре |
