# Исследование — конвейер артефактов: от сигнала до кода

> Вопрос владельца (2026-09-30): какие артефакты должны быть в проекте, как один
> порождает другой, и какие практики (Kanban, C4 и другие) к этому применимы.
> Исходная гипотеза: «идея → RFC → ряд спецификаций → ADR» и «история → план →
> задачи». Документ — исследование, не RFC: фиксирует текущее состояние, внешние
> практики, целевую модель и нарезку на RFC. Опирается на соседнее исследование
> «Жизненный цикл RFC» (`docs/system/research/2026-09-30-rfc-lifecycle.md`,
> ветка `rfc-lifecycle-research`, резервирует RFC 30) и не повторяет его.

## 1. Короткий ответ

Гипотеза верна по составу артефактов и неверна в двух местах по порядку:

1. **Спецификация — не продукт RFC, а то, что RFC меняет.** Живая спецификация
   у нас уже есть — capability-документы (`docs/system/capabilities/`) со
   сценариями. RFC — предложение *изменений* к ним (дельта), а при реализации
   дельта вливается в capability. Иначе каждый RFC плодит свою спецификацию,
   которая умирает после закрытия плана (то, что Böckeler называет spec-first
   против spec-anchored).
2. **ADR — не финал цепочки.** ADR рождаются из RFC в момент принятия (по
   одному на архитектурное решение) и во время реализации
   (`adr_task.relation='discovers'`). После реализации действует ADR, а не RFC.
3. **История и план — не звенья одной цепи, а две оси.** История отвечает
   «какую ценность и кому» и принадлежит capability; план отвечает «в каком
   порядке делаем» и принадлежит RFC (или постоянному потоку работ). Задача
   висит на обеих осях: `task → story` и `task → plan_section`. Это карта
   историй Паттона: по горизонтали — capability и истории, по вертикали —
   срезы-планы.
4. **Не всякая идея достойна RFC.** Нужны треки по размеру (S/M/L), иначе
   тяжёлый процесс будет навязан мелочи — главная претензия к spec-driven
   инструментам (Kiro пишет спеку на баг в одну строку).
5. **Человек нужен в одной точке** — точке обязательства (commitment point
   Kanban, betting table Shape Up): выше неё агенты свободно плодят и
   выбрасывают варианты, ниже — всё обещано и измеряется.

Выводы:

- Из 11 видов артефактов порождение одного другим реализовано ровно одно
  (finding → task). Остальные связи — ссылки, которые кто-то должен не забыть
  поставить; на живой БД они пусты (`story_link`, `scenario_link`,
  `open_question_link`, `plan.parent_doc_id` — ноль строк).
- Машина состояний проверяется только у задачи. У документа, истории и ADR
  `update_status` принимает любой переход.
- Верхнего слоя (идея, вариант, ставка) нет вовсе: всё, что попало в БД,
  сразу становится задачей в плане.

## 3. Внешние практики и что из них берём

Полный разбор источников — в журнале сессии; здесь только переносимое.

| Практика | Суть | Что берём | Что не берём |
|---|---|---|---|

| **Shape Up** | pitch: проблема, appetite, решение, кроличьи норы, no-gos; betting table; нет вечного бэклога | appetite и no-gos как обязательные поля RFC — ограничивают агента в раздувании скоупа; «ставка» = принятие RFC; невзятые идеи протухают, а не копятся | 6-недельные циклы и даты (ROADMAP:408: дедлайнов нет) |

| **GitHub Spec Kit** | constitution → specify → clarify → plan → tasks → analyze → implement; `[NEEDS CLARIFICATION]` | неясности = открытые вопросы, блокирующие переход; `analyze` = запрос согласованности артефактов перед исполнением; «Complexity Tracking» — обоснование отступления от принципов | ветка и папка на каждую фичу, генерация объёмного markdown |
| **Kiro** | requirements (EARS) → design → tasks; steering-файлы с условиями подключения | критерии приёмки в EARS или Given/When/Then — типизированной строкой, к которой цепляются сценарии и задачи | IDE-специфику |
| **BMAD** | PRD → архитектура → истории; readiness-гейт; история = самодостаточный пакет контекста с уроками прошлых историй | пакет контекста задачи собирается из связей (история → RFC → ADR → секция capability) под бюджет токенов — расширение `context_get` | ролевые персоны агентов |
| **RFC-процессы** (Oxide RFD, PEP, KEP) | собственный статус предложения, «реализовано» — производное, отклонение с причиной | всё это уже в исследовании RFC 30 | — |
| **ADR** (Nygard, MADR 4, Y-statement) | неизменяемость, supersede; MADR `Confirmation` — как проверяется соблюдение | поле `confirmation` → ссылка на тест-фитнес-функцию; Y-statement как однострочная сводка ADR | RACI-поля MADR (decision-makers/consulted) — один человек |
| **Fitness functions** (эволюционная архитектура) | исполняемые проверки архитектурных свойств | наши anti-drift тесты — уже фитнес-функции; связать их с ADR | — |
| **C4 + Structurizr** | модель отдельно от видов; Context → Container → Component → Code; `!adrs` привязывает решения к элементам | уровни Container/Component выводить из RFC 24 structure, Context — ручной маленький слой; ADR и capability привязываются к элементу; рендер — mermaid C4 | отдельный DSL-файл как источник истины — источник у нас БД |
| **arc42** | 12 разделов архитектурного описания | сверить дерево документации: у нас нет разделов «качество», «риски и техдолг», «глоссарий» | шаблон целиком |
| **Карта историй** (Patton), **INVEST**, **SPIDR**, **Example Mapping** | backbone активностей, срезы-релизы; критерии нарезки; правила/примеры/вопросы | история готова, когда у каждого правила есть пример-сценарий и нет открытых вопросов (красные карточки); SPIDR — в скилл нарезки | ручные сессии |
| **Impact Mapping / Opportunity Solution Tree** | цель → акторы → влияние → поставки; поставка без цели отрезается | RFC обязан назвать цель из vision; позже — сущность `goal` над историями | полное дерево возможностей — избыточно для одного владельца |
| **Diátaxis** | tutorial / how-to / reference / explanation, не смешивать | атрибут у документов-гайдов; проверка здоровья дерева | перекраивать всё дерево |
| **Living Documentation**, docs-as-code, DDD | один источник истины, сверка, генерация из кода; единый язык | уже основа cod-doc; глоссарий — BPR-006 | — |
| **Контекст-инжиниринг** (Anthropic, Cline Memory Bank, Cursor/Kiro rules) | минимальный набор сигнальных токенов, подгрузка по требованию, правила с условием подключения | короткие структурированные строки вместо длинной прозы; AGENTS.md как проекция правил из БД | Memory Bank как файлы — у нас БД |

Главное предостережение из критики SDD (Böckeler, Thoughtworks Radar 33/34):
агенты игнорируют длинные спецификации, а человек не читает сгенерированный
markdown. Отсюда правило для всего конвейера: **каждый переход проверяется
запросом по структурированным полям, а не чтением прозы**.

## 4. Целевая модель

### 4.1. Две зоны и одна точка обязательства

```
            ЗОНА ВАРИАНТОВ (агенты, выбрасывать можно)       │  ЗОНА ОБЯЗАТЕЛЬСТВ (обещано, измеряется)
                                                            │
 finding ─┐                                                 │
 question ┼─► idea ──triage──► S ─────────────────────────► │─► task (поток capability)
 audit   ─┤        (размер)    M ─► story (+критерии) ────► │─► tasks
 человек ─┘                    L ─► RFC ─┬─ open questions  │
                                         ├─ ADR proposed    │
                                         └─ дельты capability
                                              │             │
                                              └── ACCEPT ───┼─► ADR accepted (+confirmation)
                                                  (человек) │─► stories (+критерии)
                                                            │─► plan(parent=RFC) → tasks
                                                            │        │ Kanban: WIP, SLE, возраст
                                                            │        ▼
                                                            │   scenarios verify критерии
                                                            │   дельты → capability, C4 обновлён
                                                            │   план закрыт → RFC implemented
                                                            │   → release notes → audit-отчёт
```

### 4.3. Треки по размеру

Порог уже записан в скилле `rfc-authoring` (2+ слоя, новая сущность или 5+
задач → RFC); его нужно сделать полем идеи и проверкой, а не советом.

| Трек | Когда | Путь | Человек |
|---|---|---|---|
| **S** | одна задача, без новой сущности и решения | идея → задача в потоковом плане capability | не нужен сверх обычного review |
| **M** | 2–4 задачи в одном слое, пользовательская ценность | идея → история с критериями → задачи в потоковом плане | подтверждает историю (accepted) |
| **L** | порог RFC | идея → RFC → принятие → ADR + истории + план | принимает RFC — единственный обязательный гейт |
| **Expedite** | прод сломан | находка → задача с классом expedite | постфактум |

Потоковый план — постоянный план на capability (`scope=stream-<capability>`)
для работ S/M без RFC. Он снимает вопрос «куда класть задачу без RFC» и
даёт истории M-трека естественный дом.

### 4.4. Ответ на «история → план → задачи»

Не цепочка. История живёт под capability и переживает любой план: она
`delivered`, когда покрыты её критерии, а не когда закрыт план. План — срез
исполнения, привязанный к RFC или потоку. Задача несёт обе привязки. Тогда:

- «что осталось по истории» — задачи истории по всем планам;
- «что осталось по RFC» — задачи его плана по всем историям;
- карта историй = capability × план, вычисляемая, а не рисуемая.

Это согласуется с STL-003/004 (история обязательна для задачи, FK-таблица
`story_task`) и заменяет STL-002 («история → план» одной ссылкой) на
производную связь через задачи.

### 4.5. Поток при ИИ-исполнителе: качество и бюджеты вместо WIP

Решение владельца (2026-09-30): WIP-лимит ограничивал команду людей, а ИИ
пишет код конвейером — число задач в работе не узкое место. Узких мест два,
и оба — не про исполнение:

1. **Внимание человека.** Агент производит быстрее, чем человек принимает.
   Всё, что ждёт решения человека (RFC `review`, задачи `in_review`,
   согласования `approval`, истории `draft`), — единственная очередь, где
   закон Литтла по-прежнему работает: растёт очередь при постоянной
   пропускной способности человека — растёт время до решения.
2. **Бюджет мощностей.** Токены, деньги, лимиты провайдеров (Ollama Cloud,
   OpenRouter, подписка Claude). Сейчас cod-doc их не видит: колонки
   `agent_run.llm_tokens_in/out` есть, но на живой БД 0 из 20 строк
   заполнены — агенты работают снаружи (Claude Code), а их расход читает
   только офлайн-скрипт `scripts/agent_usage_report.py`. Тип согласования
   `budget` заведён и не используется.

Метки времени переходов уже есть (`activity_event`, `task_metrics`), поэтому
большая часть — запросы, а не новая схема.

| Элемент | Реализация |
|---|---|
| Точка обязательства | `backlog` = вариант (не обещано), `todo` = обещано. Сейчас доска сливает их (`_KANBAN_COLS`) — разделить колонки; переход backlog → todo = пополнение |
| Очередь решений человека | одна сводка «ждёт тебя»: RFC `review`, `in_review`, `approval pending`, истории `draft`; возраст каждого пункта; пункт `curator_next` при росте очереди |
| Качество как сигнал потока | доля возвратов `in_review → in_progress`, переоткрытые задачи, находки на свежем коде (`finding` в `affected_file` недавно закрытых задач), задачи, закрытые через `force` (BPR-001) — метрики на задачу, тип и агента |
| Бюджет | расход на задачу и план: приём usage из транскриптов харнесса (то, что сейчас делает `agent_usage_report.py`) в `agent_run`/`trace_call`; бюджет у RFC рядом с appetite; превышение — согласование `budget` |
| SLE | p85 `in_progress_hours` по типу задачи — прогноз для человека, а не лимит |
| Стоящая задача | `in_progress` старше SLE — пункт `curator_next` (дополняет 24-часовой `task_stale`) |
| Пересечение правок | параллельные агенты ограничиваются не числом, а непересечением `affected_file`: `task_checkout` предупреждает, если файлы задачи заняты другой задачей в работе |
| CFD, throughput, scatter | веб-страница метрик из `activity_event` |
| Явные политики | DoD колонки Done = BPR-001; DoR колонки Todo = готовность (§4.6) |
| Классы обслуживания | expedite / standard / intangible (техдолг); `priority` — порядок внутри класса |

### 4.6. Готовность как запрос, а не чек-лист

Переход проверяется запросом по полям (правило из §3):

| Переход | Условие |
|---|---|
| идея → RFC | размер = L, указана цель |
| RFC → accepted | нет открытых блокирующих вопросов; appetite и no-gos заполнены; у каждой дельты есть целевая секция capability (RFC 30 + дельты) |
| история → accepted | ≥1 критерий; у каждого критерия форма (EARS/GWT); нет блокирующих вопросов |
| план → исполнение (readiness, аналог BMAD / Spec Kit `analyze`) | у каждой задачи acceptance; задача привязана к истории; у каждого критерия задача или сценарий; нет циклов; ADR решений RFC существуют |
| задача → done | acceptance не пуст (BPR-001) |
| план закрыт → RFC implemented | вычисляется; дельты влиты в capability |
| ADR accepted | заполнен `confirmation` или явное «не проверяется машинно» |

### 4.7. C4 без второго источника истины

- **Context** (люди, внешние системы, наша система) — маленькая ручная таблица
  элементов и связей: этого нет ни в коде, ни в снимке.
- **Container / Component** — вид над RFC 24 (`code_boundary`, `code_entity`,
  `edge`): рисовать заново то, что уже снято с кода, — второй источник, который
  разъедется.
- **Code** — не рисуем (C4 сам считает его необязательным).
- Привязки: ADR ↔ элемент, capability ↔ элемент (аналог `!adrs` в
  Structurizr). Тогда «какие решения и задачи трогают контейнер X» — запрос
  через `affected_file` → `code_boundary`.
- Рендер — mermaid `C4Context`/`C4Container` в проекции документа
  `architecture` (гайд уже просит C4-context, ADO-053 предлагал экспорт).

## 6. Чего не делаем и почему

| Не делаем | Почему |
|---|---|
| Спецификацию на каждую фичу отдельным файлом (Spec Kit, Kiro) | spec-first: умирает после реализации; у нас живая capability |
| Даты, спринты, appetite в неделях | решение владельца (ROADMAP:408); appetite выражаем в числе задач и затронутых слоях |
| Отдельный C4 DSL как источник | второй источник истины рядом со снимком структуры |
| Генерацию кода из спецификации (Tessl) | не прижилось даже у автора подхода |
| Обязательный RFC для всего | главная претензия к SDD — один тяжёлый процесс на любой размер |
| RACI, стейкхолдеры, каденции встреч | один человек |
| WIP-лимит на число задач в работе | ограничение команды людей; для ИИ узкие места — внимание человека и бюджет (§4.5) |
| Автоматическое протухание идей | решение владельца: судьба невзятой идеи — ответственность пользователя; система не закрывает и не напоминает |

### 7.1. Изменения к спецификации: как RFC описывает правку capability

Живой пример. Будущий RFC 31 хочет, чтобы открытый вопрос можно было
превратить в идею. Затронута таблица операций `### 2.1 Операции` в
`docs/system/capabilities/decisions-and-questions.md` — в ней появляется
строка «Превратить в идею | `cod-doc question to-idea Q-021` |
`question_to_idea`».

**A. Структурная дельта** — строка в БД на каждую правку, текст пишется в RFC:

```
spec_delta:
  rfc: proposals/31-idea-intake
  target: docs/system/capabilities/decisions-and-questions#21-операции
  op: MODIFIED
  base_hash: 3f9c…            # хэш секции на момент написания RFC
  new_body: |                  # полный новый текст секции
    | Операция | CLI | MCP |
    …
    | Превратить в идею | `cod-doc question to-idea Q-021` | `question_to_idea` |
```

**B. Проза с якорем** — раздел RFC «Изменения спецификации»:

```
- decisions-and-questions §2.1 «Операции»: добавить операцию «превратить
  вопрос в идею» (CLI question to-idea, MCP question_to_idea).
```

**C. Гибрид — адрес и намерение в RFC, текст при вливании:**

```
spec_delta:
  rfc: proposals/31-idea-intake
  target: …/decisions-and-questions#21-операции
  op: MODIFIED
  base_hash: 3f9c…
  intent: "добавить операцию «превратить вопрос в идею»: CLI question to-idea, MCP question_to_idea"
  merged_revision: null        # заполняется, когда секция переписана после закрытия плана
```

| Критерий | A. Структурная | B. Проза | C. Гибрид |
|---|---|---|---|
| Цена для агента при написании RFC | высокая: переписать секцию целиком, пока реализации нет | низкая | низкая: адрес + одна фраза |
| Актуальность текста к моменту вливания | плохая: текст пишется до реализации и устаревает (урок RFC 21 — «Текущее состояние» устарело до старта) | — | хорошая: текст пишется по факту реализации |
| Проверка «дельта влита» | точная: секция = `new_body` | никакая: только чтение глазами | по факту: у целевой секции есть ревизия после закрытия плана, `merged_revision` заполнен |
| Конфликт двух RFC на одной секции | ловится `base_hash` | не ловится | ловится `base_hash` |
| Ревью человеком | тяжёлое: полный текст секции | лёгкое | лёгкое: список «где и что» |
| Секция удалена/переименована до вливания | ловится (якорь не найден) | не ловится | ловится |
| Новая сущность в схеме | да | нет | да (та же, что A, без тела) |

**Рекомендация: C.** Из A берётся всё проверяемое (адрес, операция,
`base_hash`, отметка о вливании), из B — дешевизна написания. Точный текст
пишется один раз — по реализованному коду, когда он уже известен. Readiness
RFC: у каждой дельты цель существует (или `op=ADDED` с родительской секцией).
Закрытие плана: каждая дельта влита, иначе RFC не переходит в `implemented`.
Ограничение: C проверяет, что секцию *тронули*, а не что её переписали
*правильно* — это остаётся ревью (или LLM-вердиктом куратора RFC 28).

### 7.2. Форма критерия приёмки: EARS или Given/When/Then

Живой пример — BPR-001 (DoD в `task_complete`). Факт: в `story_acceptance`
0 строк — ни у одной из 31 истории нет структурированного критерия, так что
форма выбирается на чистом месте.

**EARS** (шаблоны: ubiquitous / WHEN событие / WHILE состояние / IF
нежелательное THEN / WHERE опция):

```
1. WHEN task_complete вызван для задачи с пустым acceptance,
   THE SYSTEM SHALL отказать с ошибкой, называющей task_update --acceptance.
2. IF передан force=true без reason, THEN THE SYSTEM SHALL отказать.
3. WHEN task_complete вызван с force=true и reason,
   THE SYSTEM SHALL закрыть задачу и записать reason в revision и activity event.
4. THE SYSTEM SHALL выставлять force/reason одинаково в MCP и CLI.
```

**Given/When/Then:**

```
Сценарий: закрытие задачи без acceptance
  Дано задача BPR-X в статусе in_progress с пустым acceptance
  Когда агент вызывает task_complete(BPR-X, commit=abc123)
  Тогда ответ — ошибка с текстом «task_update --acceptance»
  И статус BPR-X остаётся in_progress
  И activity event не создан

Сценарий: обход с причиной
  Дано … Когда task_complete(BPR-X, force=true, reason="спайк") Тогда …
```

| Критерий | EARS | Given/When/Then |
|---|---|---|
| Что описывает | **правило** — одно требование одной фразой | **пример** — один прогон с конкретными данными |
| Объём на BPR-001 | 4 строки | 3–4 сценария по 4–6 строк |
| Неповеденческие требования (паритет поверхностей, инварианты, производительность) | естественно: ubiquitous-шаблон (п. 4) | неуклюже: приходится выдумывать «Когда» |
| Проверка формы машиной | ключевые слова шаблона | Дано/Когда/Тогда |
| Совпадение с нашими сценариями (`scenario`: preconditions / steps / expected) | нет, 1 правило → N сценариев | прямое: Дано = preconditions, Когда = steps, Тогда = expected |
| Вид сценария из вида критерия | IF…THEN → `error_path`, WHILE → `invariant`, WHEN → `happy_path` | не выводится |
| Писать агенту | узкий словарь, меньше воды | склонность к длинным сценариям |
| Читать человеку | быстрее: список правил | нагляднее для спорных случаев |

**Рекомендация: не выбирать, а развести по уровням — это и есть Example
Mapping.** Критерий истории (`story_acceptance`) — **правило в EARS** с
полем вида шаблона. Пример к правилу — **сценарий** (`scenario`, по сути
Given/When/Then; сущность уже есть). Readiness истории: у каждого правила
≥ 1 сценарий через `scenario_link relation=verifies to_kind=criterion` (связь
предусмотрена, 0 строк). Правило без примера — голубая карточка без зелёной;
открытый вопрос на истории — красная карточка, блокирует `accepted`.

### 7.3. Потоковый план: один на проект или на каждую capability

Потоковый план — дом для работ S/M без RFC. Сравнение по тому, как им
пользуются. Третий вариант использует то, что уже есть: секции плана —
группировка внутри плана (буква секции до двух символов, до 702 секций,
`validation/_patterns.py:19`).

| Сценарий использования | P. Один план на проект | C. План на capability (15) | S. Один план, секция = capability |
|---|---|---|---|
| Агент берёт задачу: шум соседей в контексте (`plan_ready`, `context_get`) | много: все capability вперемешку | мало | мало, если контекст режется по секции |
| Человек: «что открыто по проекту» | один запрос | `task_list` по проекту (от планов не зависит) | один запрос |
| Поиск задачи по тексту | FTS по проекту — зернистость планов не влияет | то же | то же |
| «Что осталось по capability X» | нужен фильтр по истории/capability | `plan_progress` одного плана | прогресс секции |
| Критический путь, `plan_ready` | смешивает несвязанные цепочки | чистые цепочки | цепочки внутри секции; межсекционные зависимости видны |
| Навигация в вебе и `plan_list` | 1 строка | +15 строк к 12 текущим планам | 1 строка |
| Новая capability | ничего | новый план | новая секция |
| Карта историй (capability × план) | не складывается | складывается | складывается по секции |

Вывод: «декомпозиция хороша против шума и плоха для поиска» верно для
разделения *хранилища*. Но поиск у нас идёт по проекту (FTS,
`task_list(project=…)`), а не по плану, так что зернистость планов на поиск
почти не влияет. Шум же определяется тем, по какой границе режется контекст
задачи.

**Рекомендация: S.** Один план `stream` на проект, секция на capability.
Контекст задачи режется по секции — шума как у C; `plan_list` и навигация —
как у P. Проверено 2026-09-30: `context_get` строит контекст от цели
(задачи), а не от плана, — зернистость планов на него не влияет;
`plan_ready(project, plan_scope, …)` секцию не принимает
(`mcp/tools/plan_tools.py:541`) — нужен параметр `section_letter`, как у
`task_list`. Это одна задача RFC 31, а не причина брать C.
