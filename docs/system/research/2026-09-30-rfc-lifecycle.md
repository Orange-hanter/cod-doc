# Исследование — жизненный цикл RFC и его связь с ADR

> Вопрос: RFC — это черновик ADR? Как RFC должен жить в cod-doc, если сейчас
> он неотличим от обычного документа? Документ фиксирует текущее состояние,
> целевую модель и открытые вопросы. Это не RFC: реализация, если будет
> принята, оформляется отдельным RFC и планом.

## 1. Короткий ответ

RFC не черновик ADR. Это разные сущности, отвечающие на разные вопросы:

| Вопрос | Сущность | Жизнь во времени |
|---|---|---|
| Что предлагаем и зачем? | **RFC** | после решения замораживается, остаётся историей рассуждений |
| Что решили и почему? | **ADR** | действует, пока не заменён (`superseded`) |
| Что делаем и сколько сделано? | **план + задачи** | живёт до закрытия |

Черновое состояние есть у самого ADR — `status='proposed'`. RFC при принятии
**порождает** 0…N ADR (по одному на каждое архитектурное решение внутри него)
и план; сам RFC в ADR не превращается.

Граница уже записана в `cod_doc/skills/rfc-authoring/SKILL.md`: «архитектурное
*решение* по уже принятому направлению — не RFC, а ADR». Не записано, как
одно порождает другое и как это видно в БД.

## 2. Текущее состояние (замер 2026-09-30)

| Факт | Где | Следствие |
|---|---|---|
| 29 RFC лежат документами `proposals/NN-slug` с `type=module-spec` | `document` | RFC нельзя отфильтровать по типу: тот же тип у спецификаций модулей и скиллов |
| Все 29 — `status=draft`, включая отбракованные 16–21 и давно реализованные | `document.status` | машинно не отличить живое предложение от отклонённого |
| Раздел `proposals` выбирается префиксом пути, тип не участвует | `doc_taxonomy.py`, правило `key_prefixes=("proposals/",)` | RFC вне каталога `proposals/` попадёт куда угодно |
| Статус отбраковки и причина — только проза в `proposals/README` | блок «Отбраковка 2026-08-29» | ни куратор, ни поиск эту информацию не видят |
| `plan.parent_doc_id` существует, но пуст у всех 12 планов | `plan` | связь «RFC → план» предусмотрена схемой и не используется; `doc-curator-2026-09` (RFC 25) и `agent-fit-2026-09` (RFC 27) не знают своего RFC |
| ADR — отдельная таблица с циклом `proposed → accepted → superseded / deprecated / rejected` | `adr` | у ADR цикл есть, у RFC нет |
| ADR ссылаются на задачи (`adr_task`), на ADR ссылаются секции документов (`link.kind='adr'`, 57 ссылок) | `adr_task`, `link` | обратной связи «ADR ← из какого RFC» нет |
| ADR-009, ADR-016, ADR-017 висят в `proposed` без RFC-родителя | `adr` | `proposed` ADR используется как черновик решения вне обсуждения, которому оно принадлежит |
| Вопросы (`open_question_link`) умеют ссылаться на документ и ADR, `resolved_by_adr` | `open_question_link` | инфраструктура для «открытые вопросы RFC» уже есть |

Общие статусы документа не выражают цикл RFC. `DocumentStatus` — семь
значений на все типы; стандарт frontmatter (§2b) сворачивает `accepted` в
`active`, а `rejected` и `superseded` — в `deprecated`. Записать RFC статус
`accepted` в frontmatter сейчас можно, но в БД он станет неотличим от любого
`active`-документа, а `rejected` — от устаревшего.

## 3. Как это устроено в зрелых процессах

| Процесс | Статусы | Что происходит при принятии |
|---|---|---|
| Python PEP | Draft → Accepted → Final; Rejected, Withdrawn, Deferred, Superseded | PEP становится нормативным; статус хранится в заголовке PEP |
| Kubernetes KEP | provisional → implementable → implemented; deferred, rejected, withdrawn, replaced | KEP разрешает реализацию; прогресс ведётся по стадиям релизов |
| Rust RFC | обсуждение PR → merge = accepted → tracking issue | реализация отслеживается отдельной задачей, текст RFC больше не правится |
| ADR (Nygard) | proposed → accepted → deprecated / superseded | запись неизменна, изменение решения — новый ADR |

Общее у всех:

1. У предложения есть **собственный** статус, отдельный от статуса реализации.
2. «Реализовано» — производное от трекера реализации, а не ручная отметка.
3. Принятый текст замораживается; изменения идут новым документом с
   `superseded_by`.
4. Отклонение — полноценный статус с причиной, а не удаление.

## 4. Целевая модель

### 4.1. Жизненный цикл RFC

```
draft → review → accepted → implemented
            ↘ rejected
draft/review → withdrawn
accepted/implemented → superseded (by RFC N)
```

| Статус | Смысл | Кто переводит |
|---|---|---|
| `draft` | автор пишет | автор |
| `review` | обсуждение; спорные развилки — открытые вопросы или ADR `proposed` | автор |
| `accepted` | решение принято, реализация разрешена | человек; переход запрещён при открытых блокирующих вопросах |
| `implemented` | план RFC закрыт | **вычисляется** из статуса плана |
| `rejected` | отклонено, причина обязательна | человек |
| `withdrawn` | автор снял предложение | автор |
| `superseded` | заменено RFC N | при принятии заменяющего RFC |

### 4.2. Что происходит при `accepted`

1. Каждое архитектурное решение внутри RFC становится ADR: `proposed` →
   `accepted`, либо создаётся новый ADR. ADR получает ссылку на RFC-родитель.
2. Создаётся план со scope `rfc-NN-slug`, `plan.parent_doc_id` указывает на RFC.
3. Тело RFC замораживается: дальше допустимы только правки ошибок. Устаревание
   фиксируется новым RFC, а не правкой старого (урок RFC 21: «Текущее
   состояние» устарело раньше старта реализации).

После этого «почему так» читается из ADR, «что делаем» — из плана, а RFC —
история рассуждений, к которой возвращаются редко.

### 4.3. Где хранить

| Вариант | За | Против |
|---|---|---|
| **A. Документ `type=rfc` + собственные поля статуса** | RFC — длинная проза с секциями; секции, ссылки, drift, FTS, проекция уже работают для документов | нужны поля вне общего `DocumentStatus` |
| B. Отдельная таблица `rfc`, как `adr` | строгая схема и цикл | теряется вся механика документов, тело придётся хранить заново |
| C. Документ + статус в общем `DocumentStatus` | ноль миграций | §2b сворачивает `accepted`/`rejected` в `active`/`deprecated` — цикл теряется |

Рекомендуется **A**. ADR — короткая структурированная запись, поэтому
таблица ему подходит; RFC — нет.

Состав варианта A:

- `DocumentType.RFC = "rfc"`; бэкфилл 29 документов `proposals/NN-*`
  (не `proposals/README`, он остаётся индексом);
- поля RFC: `rfc_status` (цикл из §4.1), `rfc_number`, `superseded_by`,
  `decision_reason` — отдельная таблица `rfc_meta` 1:1 к `document` или
  колонки на `document`; выбор — открытый вопрос §5;
- связь RFC → план — существующий `plan.parent_doc_id`;
- связь RFC → ADR — новое поле `adr.source_doc_id` (или ребро в `link`);
- открытые вопросы RFC — существующий `open_question_link`
  (`to_kind=document`, `relation=blocks`);
- правило раскладки по типу `rfc` → раздел `proposals`, а не только по
  префиксу пути;
- `proposals/README` — генерируемая проекция таблицы RFC со статусами вместо
  ручной.

### 4.4. Контроль куратором

Новые пункты очереди `curator_next` / рутины:

| Нарушение | Действие |
|---|---|
| RFC `accepted` без плана | создать план |
| RFC `accepted` без ADR при затронутой архитектуре | извлечь ADR |
| план закрыт, RFC не `implemented` | вычислить статус |
| RFC `draft`/`review` без изменений N дней | решить: принять, отклонить, снять |
| ADR `proposed` без RFC-родителя дольше N дней | привязать к RFC или принять/отклонить |
| RFC `accepted` с открытым блокирующим вопросом | закрыть вопрос или откатить статус |

### 4.5. Поверхности

По правилу «четырёх равных поверхностей» переходы RFC выставляются в CLI
(`cod-doc rfc new/list/show/accept/reject/withdraw/supersede`) и MCP
(`rfc_*`, профили `standard`/`full`), веб — список RFC со статусами и
детальная страница со связанными ADR, планом и вопросами. Скилл
`rfc-authoring` переписывается под цикл; `adr-author` получает шаг
«привязать к RFC-родителю».

## 5. Открытые вопросы

1. Поля RFC — колонки на `document` или таблица `rfc_meta`? Колонки проще,
   но добавляют `document` полей, пустых у 95% строк; миграции, трогающие
   `document`, нельзя делать через `batch_alter_table` (CLAUDE.md).
2. `implemented` — хранимое значение, пересчитываемое при закрытии плана, или
   вычисляемое при чтении? Хранимое нужно для FTS и фильтров.
3. Связь RFC → ADR — колонка `adr.source_doc_id` (один родитель) или ребро в
   `link` (много)? Один ADR, обсуждённый в двух RFC, — реальный случай или
   нет?
4. Бэкфилл статусов 29 RFC: кроме 16–21 (отбракованы 2026-08-29) статусы
   придётся восстанавливать по README и планам вручную. Кто решает спорные?
5. Нумерация: `rfc_number` из имени файла или счётчик в БД, как у ADR
   (`max+1`)? README требует, чтобы номер не переиспользовался даже после
   отклонения.
6. Нужен ли статус `deferred` (PEP, KEP)? Сейчас «отложено» и «отклонено»
   в README не различаются.

## 6. Следующий шаг

Если модель принимается — RFC 30 «Жизненный цикл RFC» по шаблону
`rfc-authoring` и план `rfc-lifecycle` на 5–7 задач: тип и поля + миграция
с бэкфиллом; связи с планом и ADR; переходы в сервисе и на четырёх
поверхностях; генерация README; проверки куратора; правка скиллов
`rfc-authoring` и `adr-author`.
